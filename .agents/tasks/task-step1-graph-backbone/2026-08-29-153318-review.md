# Durable graph + vector backbone for Quant Feed (Step 1) — review pass (v1)

Step 1 swaps the ephemeral `/tmp`-JSON relationship store for a real backend: a Python 3.11 FastAPI + Celery service under `backend/` backed by Neo4j (graph), Qdrant (vectors), and Postgres (system-of-record), plus an entity-aware NLP pipeline that runs NER with custom finance labels, OpenAI (or an offline local-hash) embeddings, and three-axis relationship scoring (semantic cosine + IDF entity overlap + LLM causal), producing a composite edge weight `0.35*semantic + 0.25*entity_overlap + 0.40*causal`. A read API (`/graph/query`, `/articles/{id}`, `/health`) serves the exact `GraphData`/`EconomicEdge`/`TopicCorrelation` JSON the Next.js app already consumes, and the frontend proxies to it only when `BACKEND_URL` is set, falling back to the existing live-fetch path otherwise. The contract fidelity is tight — camelCase aliases, `link.strength == composite weight`, and a color map that matches `lib/news/store.ts` exactly.

Watch for: the frontend proxy calls `/graph/query` directly without consulting `/health`, so a reachable-but-slow backend adds up to a 4s stall before the fallback fires (confirmed); Neo4j `RELATES_TO` edges are written by ingestion but the read API never reads them back — edges are served from Postgres only, so Neo4j is effectively write-only in Step 1 (confirmed); the backfill's "non-empty graph offline" guarantee only covers the embedder and causal classifier, not the fetch stage, which still needs network (confirmed); and the entire live datastore round-trip (compose up → alembic → backfill → serve) is unexercised because the sandbox container runtime is broken — a known infra constraint, but it means the Postgres string→timestamp coercion and the Neo4j/Qdrant health pings have never actually run against a real store (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend fallback is the safety-critical surface and it is sound: `isBackendEnabled()` gates the whole proxy branch on `BACKEND_URL`, `safeGetJson` never throws and enforces a 4s `AbortController` timeout, and an empty/`null` result falls through to the unchanged live-fetch → `/tmp` → mock chain. With `BACKEND_URL` unset the branch is dead code, so the deployed Vercel prototype behaves exactly as before. The rough edge is latency: there is no `/health` pre-check, so a slow-but-alive backend costs the full timeout on every request before falling back.

The contract mapping is asserted against `lib/types.ts` and `lib/news/store.ts` in tests (color map, node/link field names, `strength == weight`). Sentiment is the exception: there is no sentiment anywhere in the domain model, so the backend *derives* it from `economicImpactScore` thresholds — a new, backend-only filter axis the frontend fallback path cannot reproduce, so the same `sentiment=` query returns different results depending on whether `BACKEND_URL` is set.

The scoring math is exact (smoothed IDF, weighted-Jaccard overlap, clamped weighted-sum composite) and screening runs before the expensive causal classifier. The offline heuristic classifier always returns `related` with a fixed confidence, so offline edge weights are driven entirely by semantic + entity overlap and are not comparable in kind to online LLM-scored edges.

Ingestion dual-writes edges to Postgres and Neo4j, but the read API only reads Postgres, so Neo4j `RELATES_TO` edges are dead weight (and a silent divergence risk) for Step 1 reads.

The biggest gap is verification depth, not code. Everything is proven with fakes, in-memory stores, and `TestClient`; no code path that touches a real Neo4j/Qdrant/Postgres has executed, leaving the string→`DateTime` column coercion, the health pings, and idempotency-under-real-constraints unverified.

### Frontend fallback safety and the missing health gate

The proxy result is used only when `backendGraph && backendGraph.nodes && backendGraph.nodes.length > 0`; anything else — `null`, empty nodes, or a thrown error — falls straight through to the untouched live-fetch → `/tmp` → mock logic, and `safeGetJson` returns `null` on non-2xx, bad JSON, abort, or any throw. With `BACKEND_URL` unset the entire branch is skipped.

The gap is latency, not correctness. There is no `/health` consultation before the proxy attempt (the FEAT-004 findings describe using `/health` "to decide whether to proxy or fall back," but the shipped code does not). A backend that is up but slow — cold Lambda, saturated DB pool, a hanging Neo4j ping — costs the full `BACKEND_TIMEOUT_MS` (4000ms) on *every* `/api/graph` request before the fallback fires, and the user sees a 4-second stall instead of the instant live-fetch path. A health gate with a tighter timeout, or a shorter connect/first-byte budget on the graph call itself, would bound this.

One asymmetry rides along here: the proxy passes `sentiment` and `entity` to the backend, but when it falls through, the live-fetch path in the same handler only implements `category` and date-range filtering — there is no sentiment or entity filter on the fallback. So `?sentiment=positive` narrows results when `BACKEND_URL` is set and is silently ignored when it isn't.

### Sentiment as a derived, backend-only axis

There is no sentiment field in `lib/types.ts`, the Postgres schema, or `ArticleIn`. `filter_articles` synthesizes it from `economic_impact_score`: `>=7` positive, `<=3` negative, else neutral. This is a semantic overload — a high *economic impact* score is not the same as positive *sentiment*; a market crash scores high impact and would read as "positive" here. Combined with the fallback path having no sentiment filter at all, the same query string produces materially different graphs depending on deployment state. Either document this as an explicit Step-1 approximation or defer the sentiment filter until a real sentiment signal exists.

### Persistence topology: Neo4j edges are written but never read

```
ingest ─┬─> Postgres  (Article, Entity, ArticleEntity, Edge)   <── read API reads HERE
        ├─> Neo4j     (:Article, :Entity, [:MENTIONS], [:RELATES_TO])   (RELATES_TO unread)
        └─> Qdrant    (article_embeddings)                       (searched only during ingest)
```

`orchestrator.run` dual-writes every scored edge to Postgres (`upsert_edge`) and Neo4j (`upsert_relates_to`), but `PostgresReadStore` — the only concrete `GraphReadStore` — reads edges exclusively from the Postgres `Edge` table. The `graph_service` docstring frames Neo4j as "an equivalent edge source," yet nothing in the read path touches it. For Step 1 the Neo4j `RELATES_TO` write is pure overhead and a latent divergence risk: the two stores can drift (a failed Neo4j upsert after a successful Postgres commit) with no reader to notice. Defensible as forward-investment for a later Graph-RAG step, but it should be called out so a reader doesn't assume the graph query is Neo4j-backed.

### Scoring math and offline weight inconsistency

The exact `0.35/0.25/0.40` arithmetic and config-weight propagation are asserted in tests, so a reverted formula would fail. The concern is offline consistency: `HeuristicCausalClassifier` always emits `relationship="related"`, `direction="source->target"`, fixed confidence, so offline edges carry a constant causal term and their weight is driven entirely by semantic + entity overlap. If a backfill runs offline and later ingestions run online (LLM-scored), edge weights across the graph are not comparable in kind.

### Offline backfill fetch gap

`select_embedder`/`select_causal_classifier` make the *scoring* half offline-safe. The *fetch* half is not: `fetch_live_news` only pulls RSS + Guardian over `httpx`, degrading to `[]` on failure. With no network, `articles` is empty and the script logs "No articles fetched; nothing to backfill" and exits 0 — an empty graph. The offline guarantee stated in the module docstring and FEAT-002 ("so the backfill still populates a non-empty graph") therefore holds only when the network is reachable but `OPENAI_API_KEY` is absent, not when fully offline. Either narrow the claim or ship a small seed-article set for the truly-offline path.

### Verification depth: everything real is untested

The accepted sandbox constraint (podman with broken rootless networking) means no code path touching a live Neo4j/Qdrant/Postgres has run. Two concrete risks hide behind that:

- `schema_map.article_row` puts the ISO `published_at` *string* into `Article.published_at`, a `DateTime(timezone=True)` column. A malformed or naive-vs-aware edge case would only surface against a real DB. On the read side `_article_from_row` handles both `datetime` and string, so the round-trip is asymmetric (string in, datetime-or-string out).
- `/health` pings (`Neo4jStore.verify_connectivity`, `QdrantStore.ping`, Postgres `SELECT 1`) are only ever exercised with the checks patched, so the actual driver calls are unproven.

`PostgresRelationalStore` also commits once per entity (`upsert_entity`), once per article-entity link, and once per edge — idempotent by natural key, but at backfill scale that is a large number of tiny transactions; batching per article or per run would matter once real volumes flow.

### Secret hygiene

`.env.local` is neither tracked nor in the diff; the only env files changed are `.env.example` and `backend/.env.example`, both with empty placeholders. A scan of the diff for concrete key/password/token values turned up nothing, and `OpenAIEmbedder`/`OpenAICausalClassifier` take the key via constructor and never log it.
